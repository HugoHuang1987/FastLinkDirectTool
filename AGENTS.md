# FastLink direct helper engineering rules

- Preserve the user's FastLink process, Wi-Fi connection and credentials. Keep automatic FastLink restart off unless the user explicitly enables it.
- Never stop the DNS listener or replace a running helper while helper-owned NRPT rules may still reference it. Check exit status, timeout and actual rule readback before proceeding; only remove rules with this tool's ownership marker.
- Treat source, configuration and binaries as user-owned. Back up before deploying; do not use a hard process kill as a normal build/deploy step.
- Run `tests/Run-RegressionTests.ps1` and compile before deployment. Cover a full-size rule set, including the Windows command-line length fallback, not just one test rule.
- Verify real DNS answers by requested hostname or a validated CNAME chain; do not mistake additional-section name-server addresses or FastLink fake-IP answers for target IPs.
- After deployment, verify helper DNS UDP/TCP listeners, exact physical DNS route, internal HTTPS targets, proxy transport, unchanged VPN PIDs, and live scheduler state. A homepage response is not proof of Exchange account authentication.
- Keep generated diagnostics and backups outside this repository under the current `codex_tasks` task directory. Never persist VPN or mail credentials in logs or artifacts.
- A pending cleanup must gate automatic network refresh, rule application and expired-route maintenance even when the DNS listener is still running. A failed network refresh must pause automatic retry and notify once; a new physical network must be stable for at least eight seconds before refresh. Preserve phase/progress logs and bounded timeouts for full NRPT lists.
- Preserve rule edits made while any background operation is busy. Capture the rule revision and private-network option with each apply snapshot; acknowledge only that revision and drain the latest complete list after the operation finishes. Never clear newer pending edits, bypass cleanup/network stability gates, or retry failed applies indefinitely.
- Keep AnyDesk diagnostics passive and in the existing hidden monitor. Parse only allowlisted metadata from bounded incremental trace reads; never persist raw lines, remote IDs, accounts, secrets, screen/input/clipboard contents or packet payloads. Cap retention and back off slow collectors. Report generation is on demand, never periodic AI work. System-wide counters and TUN interception are not per-session loss or proof of an overseas proxy.
- System-proxy compatibility must verify Fastlink GUI/core paths and loopback listener PID ownership; unknown proxies and aTrust are not FastLink. Preserve legacy TUN detection. Build all three production C# sources and run detection/bypass fake-storage tests with the existing regression suite.
- Modify only owned additions to ProxyOverride, never ProxyEnable/ProxyServer/PAC or another application's original bypass entries. Persist ownership before writing, verify readback, notify Windows, and fail closed on ambiguous concurrent changes. Cleanup must preserve DNS until all owned dependencies are safely removed. Never automatically restart the new ApexCore architecture.
- Safe cleanup must first drain and pause DNS-triggered route writes at the RouteManager boundary. Verify owned NRPT removal before removing owned proxy bypass entries; only then stop DNS and remove routes. Every CleanupPending path must retain this pause, while explicit cleanup remains allowed. Test asynchronous/late DNS callbacks, not only UI maintenance gates.
- Dual-network Start/Arm read-only gate failures must preserve an existing prepared session. Never treat a rejected request as authorization to restore old default-route priorities.
- Dual-network Stop/Recover need a separate, nonpersistent approval to restore interface priorities while another default exit may be online. Check again before each metric restore; unknown topology is not consent. Automatic failure handling must retain the metric journal, verify ownership/readback/egress before claiming InternetProtected, and pause retries on uncertain cleanup.
- Acceptance scripts must default to read-only preflight, never Recover/Exit/relaunch before proving readiness, never tick enterprise admission or permission confirmations on the user's behalf, and stop on any missing/disabled control or uncertain result. Offline tests and a compiled candidate are not proof of SRDPM login plus external-network acceptance.
- Mode three keeps explicit physical roles (corporate Wi-Fi, wired Internet); never infer them from adapter speed or a private IP. Preserve existing Internet IPv6 only when all broad IPv6 route evidence belongs to the named up physical Internet adapter. Missing evidence, another IPv6 egress or changed route fingerprints must block/pause, never disable IPv6 or aTrust automatically. Corporate splitting remains IPv4-only.
- Retiring an externally changed dual journal is distinct from network recovery: two complete read-only reviews, whole-document compare, persisted evidence and atomic original-file archive are required. No residual owned route/NRPT/manual metric may be abandoned. Do not invoke archive from a fresh external runtime while an old helper might still be active; establish a dedicated idle maintenance window or wait for safe shutdown.
- A user's explicit company dual-network permission may be remembered only for the current machine/user and exact unordered physical-adapter GUID pair, with source and UTC record time. Never invent or migrate permission to a different machine/pair, and never persist MOKA admission or live Internet success as permission. Every live Arm/Start must re-probe the selected IPv4 source with normal TLS and no proxy, compare snapshots, then use a topology-bound in-memory proof; expiry of a consumed proof alone must not tear down an unchanged running session. `--prepare-network-mode` is a one-shot explicit preparation request, never a logon default or authorization for full Start.
- Daily operation must not require repeated checklists. Explicit Save/Start can acknowledge fully classified rules; explicit Start may express the user's current admission assertion only when this meaning is visible next to the action. Do not label that assertion as verified MOKA authentication, persist it, or infer it from launch/minimize/show/logon. Unknown classifications still block. New machine/user/adapter pairs still require scoped permission. Keep the independent default-egress restore decision.
- UI visibility is separate from networking: X/minimize/show/settings expansion and duplicate launches must never Start/Stop/cleanup or repeat initialization. Show only the current work window; provide a desktop reopen entry that signals the existing instance. Offline UI tests must use an isolated non-input desktop when the user is working. Never install a candidate over an active DNS/journal owner.
- A prepared-but-not-running dual session must verify the selected physical adapter identities and its owned IPv4 metrics before reporting readiness. Drift or unclassified read failures must invalidate readiness and preserve the journal and current network settings; do not automatically Stop, clean up, restore priorities, or overwrite another writer. Only the existing bounded typed read-timeout deferral may postpone verification, and the UI must show that readiness is not yet verified during that deferral.
- A listening dual DNS socket is not an admitted session. Keep admission closed until every NRPT write/readback, final topology check and Running journal save succeed. Bind packets before queueing; generation/ticket checks must reject late activation and replies. Pause must invalidate admission and boundedly drain only final socket sends before dependent cleanup; a drain failure retains ownership records, listener and dependencies. Never include upstream queries or route callbacks in the send-coordination lock.
- Diagnostic file IO must not run on the platform/route critical path. Use metadata-only aggregation and at most one queued/in-flight asynchronous publication; drop diagnostics when busy and never let a blocked log sink delay networking. Command-response validation is distinct from final resource ownership/readback and business success.
